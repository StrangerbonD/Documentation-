Authentication vs Authorization

পড়ার সময়: ৬ মিনিট
মডিউল: ০২

১. এটা কী? (What are they?)

অনেকেই Authentication আর Authorization এই দুটো টার্ম গুলিয়ে ফেলে এবং ভাবে দুটো একই জিনিস। কিন্তু টেকনিক্যালি এদের কাজ একদম আলাদা:

Authentication (AuthN) — "তুমি কে?"

Authentication হলো সহজ ভাষায় ইউজারের পরিচয় নিশ্চিত করা। অর্থাৎ, একজন ব্যক্তি যে পরিচয় দাবি করছে (যেমন: তার ইমেইল বা ইউজারনেম), সে আসলেই সেই ব্যক্তি কি না, তা যাচাই করা। সাধারণত Username/Password, OTP বা বায়োমেট্রিক দিয়ে Authentication করা হয়।

Authorization (AuthZ) — "তোমার কী করার অধিকার আছে?"

Authorization হলো ইউজারের অনুমতি বা পারমিশন চেক করা। ইউজার কে তা নিশ্চিত হওয়ার পর (Authentication সফল হলে), সে অ্যাপ্লিকেশনের কোন কোন রিসোর্সে ঢুকতে পারবে বা কোন কোন ডেটা ডিলিট/মডিফাই করতে পারবে, তা নির্ধারণ করে Authorization।

২. কেন দরকার? (Why do we need both?)

ভেব দেখো, যদি একটা সিস্টেমে শুধু Authentication থাকে কিন্তু কোনো Authorization না থাকে, তাহলে কী ঘটবে?

  • যে কোনো সাধারণ ইউজার (যেমন একজন Student) সিস্টেমে লগইন করেই আরেকজনের রেজাল্ট এডিট করে দিতে পারবে বা ডেটাবেস ড্রপ করে দিতে পারবে! কারণ সিস্টেম জানে সে স্টুডেন্ট রহিম (Authentication পাস), কিন্তু রহিম অ্যাডমিনের কাজ করতে পারবে কি না (Authorization) সেটা সিস্টেম চেক করছে না।
  • আবার যদি উল্টোটা হয়—সিস্টেমে Authorization রুল আছে কিন্তু Authentication নেই, তাহলে যে কেউ না জানিয়েই অ্যাডমিন প্যানেলে ঢুকে কাজ করে ফেলতে পারবে, কারণ সিস্টেম যাচাই-ই করেনি সে আসলে কে।

তাই সিকিউর ওয়েব অ্যাপ্লিকেশনে আগে Authentication সম্পন্ন হয়, তারপর সেই ইউজারের পরিচয়ের ওপর ভিত্তি করে Authorization কাজ করে।

৩. এটা কীভাবে কাজ করে? (How does it work?)

একটি আধুনিক ক্লায়েন্ট-সার্ভার আর্কিটেকচারে (যেমন Angular/React ফ্রন্টএন্ড এবং ASP.NET Core ব্যাকএন্ড) ফ্লো-টা এভাবে কাজ করে:

  1. ইউজার লগইন রিকোয়েস্ট পাঠায়: ইউজার তার Email আর Password পাঠিয়ে /api/auth/login এন্ডপয়েন্টে একটা POST Request পাঠায়।
  2. সার্ভার পরিচয় যাচাই করে (Authentication): সার্ভার ডেটাবেস থেকে ইউজারের Password Hash চেক করে দেখে পাসওয়ার্ড সঠিক কি না। যদি সঠিক হয়, তাহলে Authentication সফল!
  3. JWT Token ইস্যু করা হয়: সার্ভার সাথে সাথে একটা সই করা JWT Token তৈরি করে ইউজারের কাছে পাঠিয়ে দেয়। এই টোকেনের ভেতরে ইউজারের নাম, আইডি এবং তার Role (যেমন: Student বা Admin) Claim হিসেবে লেখা থাকে।
  4. পরবর্তী রিকোয়েস্টে টোকেন পাঠানো: ইউজার যখন কোনো প্রোটেক্টেড এন্ডপয়েন্টে (যেমন: /api/admin/delete-user) রিকোয়েস্ট করে, তখন সে Request-এর Header-এ এই Token-টি দিয়ে দেয়।
  5. সার্ভার পারমিশন যাচাই করে (Authorization): সার্ভারের Middleware প্রথমে টোকেনটি ভ্যালিড কি না তা দেখে (Authentication), এরপর টোকেনের ভেতরে Role চেক করে দেখে ইউজারের রোল Admin কি না। যদি Admin হয় তাহলে কাজ করতে দেয় (HTTP 200), আর যদি Student হয় তাহলে আটকে দেয় (HTTP 403 Forbidden)।

৪. একটা সহজ বাস্তব উদাহরণ (Real-Life Example)

ইউনিভার্সিটির ক্যাম্পাস ও সার্ভার রুমের গল্প

ধরো তুমি তোমার ইউনিভার্সিটির মেইন গেট দিয়ে ক্যাম্পাসে ঢুকতে যাচ্ছো। গেটে সিকিউরিটি গার্ড তোমাকে থামাল এবং তোমার Student ID Card দেখতে চাইল। তুমি কার্ড দেখালে এবং গার্ড মিলিয়ে দেখল তুমি সত্যিই এই ভার্সিটির একজন স্টুডেন্ট। এটা হলো Authentication (তোমার পরিচয় নিশ্চিত হলো)।

এবার তুমি ডিপার্টমেন্টে ঢুকে সোজা ডিপার্টমেন্টাল "সেন্ট্রাল সার্ভার রুম"-এ ঢুকতে গেলে। দরজার সিকিউরিটি অফিসার বা ডিজিটাল ফিঙ্গারপ্রিন্ট স্ক্যানার তোমাকে আটকে দিল এবং বলল: "তুমি আমাদের স্টুডেন্ট ঠিক আছে, কিন্তু এই সার্ভার রুমে ঢোকার পারমিশন শুধু নেটওয়ার্ক অ্যাডমিনদের আছে, স্টুডেন্টদের নেই!" এটা হলো Authorization (তুমি কে তা জানা সত্ত্বেও তোমার পারমিশন না থাকায় তোমাকে এক্সেস দেওয়া হলো না)।

৫. কোড এক্সাম্পল (C# / ASP.NET Core)

নিচে একটি ASP.NET Core Web API কন্ট্রোলারের উদাহরণ দেওয়া হলো যেখানে Authentication এবং Authorization দুটোই ব্যবহার করা হয়েছে:

Controllers/DashboardController.cs 
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
using System.Security.Claims;

[ApiController]
[Route("api/[controller]")]
public class DashboardController : ControllerBase
{
    // ১. যে কেউ এই Endpoint দেখতে পারবে (Public)
    [HttpGet("public-info")]
    [AllowAnonymous]
    public IActionResult GetPublicInfo()
    {
        return Ok(new { message = "ভার্সিটির সাধারণ নোটিশবোর্ড—সবাই পড়তে পারবে।" });
    }

    // ২. Authentication প্রয়োজন: যে কোনো লগইন করা ইউজার ঢুকতে পারবে
    [HttpGet("profile")]
    [Authorize]
    public IActionResult GetUserProfile()
    {
        var userId = User.FindFirstValue(ClaimTypes.NameIdentifier);
        var userEmail = User.FindFirstValue(ClaimTypes.Email);

        return Ok(new { 
            message = "লগইন সফল হয়েছে!",
            userId = userId,
            email = userEmail
        });
    }

    // ৩. Authorization প্রয়োজন: শুধুমাত্র Admin রোলধারীরাই ঢুকতে পারবে
    [HttpDelete("delete-database")]
    [Authorize(Roles = "Admin")]
    public IActionResult DeleteDatabaseRecord()
    {
        return Ok(new { message = "রেকর্ড ডিলিট সম্পন্ন (শুধুমাত্র অ্যাডমিন অধিকারপ্রাপ্ত)!" });
    }
}

৬. কোডের লাইন-বাই-লাইন ব্যাখ্যা

চলো কোডের প্রতিটি গুরুত্বপূর্ণ পার্ট বিস্তারিত বুঝে নেওয়া যাক:

[AllowAnonymous] এই Attribute দিয়ে বোঝানো হয়েছে এই মেথডে ঢোকার জন্য কোনো Token বা Login লাগবে না। এটা সবার জন্য উন্মুক্ত (যেমন: নোটিশ বোর্ড বা রেজিস্ট্রেশন পেজ)।
[Authorize] এখানে শুধু Authentication চেক করা হচ্ছে। অর্থাৎ ইউজারের রিকোয়েস্টে একটি ভ্যালিড JWT Token থাকতে হবে। টোকেন ছাড়া কেউ আসলে ASP.NET Core সাথে সাথে 401 Unauthorized রেসপন্স ছুড়ে মারবে।
User.FindFirstValue(ClaimTypes.NameIdentifier) ইউজার লগইন করার সময় টোকেনের মধ্যে যে User ID Claim হিসেবে রাখা হয়েছিল, কন্ট্রোলারের User অবজেক্ট থেকে সরাসরি সেই ভ্যালু বের করে আনা হচ্ছে। এর জন্য কোনো বাড়তি ডেটাবেস কুয়েরি করতে হচ্ছে না!
[Authorize(Roles = "Admin")] এখানে Authorization প্রয়োগ করা হচ্ছে। ইউজার শুধু লগইন করলেই হবে না, তার টোকেনের ভেতরে Role Claim-এর মান অবশ্যই Admin হতে হবে। যদি কোনো সাধারণ স্টুডেন্ট এই মেথড কল করে, ASP.NET Core তাকে 403 Forbidden রেসপন্স দেবে।

৭. কমন ভুলগুলো (Common Mistakes)

ডেভেলপাররা সাধারণত যেসব মারাত্মক ভুল করে:
  • 401 আর 403 গুলিয়ে ফেলা: মনে রাখবে, 401 Unauthorized মানে "তুমি লগইন করোনি বা টোকেন ইনভ্যালিড" (Authentication ফেইল)। আর 403 Forbidden মানে "তুমি লগইন করেছো ঠিকই কিন্তু এই কাজ করার পারমিশন তোমার নেই" (Authorization ফেইল)।
  • ফ্রন্টএন্ড চেককেই চূড়ান্ত নিরাপত্তা ভাবা: শুধু React/Angular-এ "Delete" বাটন হাইড করে রাখলেই নিরাপত্তা নিশ্চিত হয় না! কেউ Postman বা cURL দিয়ে সরাসরি API কল করতেই পারে। তাই ব্যাকএন্ড কন্ট্রোলারে অবশ্যই [Authorize(Roles = "Admin")] থাকতে হবে।
  • Middleware-এর সিরিয়াল ভুল করা: Program.cs-এ সবসময় আগে app.UseAuthentication() এবং তারপরে app.UseAuthorization() লিখতে হয়। উল্টো লিখলে পরিচয় জানার আগেই পারমিশন চেক করার চেষ্টা করবে এবং সিস্টেম ঠিকমতো কাজ করবে না!

৮. শর্ট সামারি (Short Summary)

এক নজরে মূল পয়েন্টগুলো:

১. Authentication: কে তুমি? (Identity verification — যেমন: লগইন করা)। ব্যর্থ হলে HTTP Status Code 401 Unauthorized।

২. Authorization: কী করতে পারো? (Permission check — যেমন: অ্যাডমিন কি না)। ব্যর্থ হলে HTTP Status Code 403 Forbidden।

৩. আগে Authentication হয়, তার ওপর ভিত্তি করে পরবর্তীতে Authorization এক্সিকিউট হয়।
