Role-based ও Policy-based Authorization

পড়ার সময়: ৭ মিনিট
মডিউল: ০৬

১. এটা কী? (What is Role-based Authorization?)

Role-based Authorization (RBAC) হলো ইউজারের পদবী বা রোল (যেমন: Admin, Teacher, Student) অনুসারে নির্দিষ্ট API Endpoint বা ডেটায় এক্সেস নিয়ন্ত্রণ করার একটি পদ্ধতি।

আর যখন শুধু রোল যথেষ্ট হয় না, বরং জটিল শর্তের প্রয়োজন হয় (যেমন: "ইউজারের বয়স ১৮+ হতে হবে" অথবা "শুধুমাত্র ডিপার্টমেন্ট হেড হতে হবে"), তখন আমরা Policy-based Authorization ব্যবহার করি।

২. কেন দরকার? (Why do we need it?)

একটি অ্যাপ্লিকেশনে সব ইউজারের অধিকার সমান নয়। টিচারের জন্য যে এন্ডপয়েন্টে গ্রেড ইনপুট দেওয়ার অনুমতি থাকবে, স্টুডেন্টের জন্য কেবল গ্রেড দেখার অনুমতি থাকবে। কন্ট্রোলারের মেথডে if (user.Role == "Admin") লিখে ম্যানুয়াল চেক করা কোডকে নোংরা করে। ASP.NET Core ডিক্লারেটিভ অ্যাট্রিবিউট [Authorize(Roles = "...")] দিয়ে খুব সহজেই ক্লিনভাবে এই নিরাপত্তা নিশ্চিত করে।

৩. এটা কীভাবে কাজ করে? (How does it work?)

  1. লগইনের সময় টোকেনের ভেতর new Claim(ClaimTypes.Role, "Admin") দিয়ে রোলটি সিল করা হয়েছিল।
  2. যখন রিকোয়েস্ট আসে, app.UseAuthentication() টোকেন পড়ে ইউজারের আইডেন্টিটিতে সেই রোল লোড করে।
  3. কন্ট্রোলারের ওপর থাকা [Authorize(Roles = "Admin")] মিডলওয়্যার চেক করে: "ইউজারের রোলের তালিকায় কি 'Admin' আছে?"
  4. থাকলে রিকোয়েস্ট সফলভাবে মেথডে ঢুকবে। না থাকলে সার্ভার সাথে সাথে HTTP 403 Forbidden পাঠিয়ে ক্লায়েন্টকে থামিয়ে দেবে।

৪. বাস্তব জীবনের উদাহরণ (Real-Life Example)

অফিসের VIP লাউঞ্জ ও এক্সিকিউটিভ লিফট

একটি বহুতল কর্পোরেট ভবনে সাধারণ কর্মীরা যেকোনো ফ্লোরে সাধারণ লিফট দিয়ে যেতে পারে। কিন্তু ১০ম তলায় রয়েছে "Board of Directors Lounge"। সেখানে লিফটের বাটনে চাপ দিলে লিফট কার্ড সোয়াইপ করতে বলে। শুধুমাত্র যাদের আইডি কার্ডে Executive / Director স্ট্যাটাস এনকোড করা আছে, তাদের জন্য লিফট ১০ম তলায় থামে, অন্যদের ক্ষেত্রে বাটন কাজই করে না!

ASP.NET Core-এর [Authorize(Roles = "...")] হলো ঠিক সেই এক্সিকিউটিভ লিফটের ফ্লোর রেস্ট্রিকশন।

৫. কোড এক্সাম্পল (C# Controller ও Program.cs Policy)

Controllers/CoursesController.cs 
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;

[ApiController]
[Route("api/[controller]")]
public class CoursesController : ControllerBase
{
    // ১. যে কোনো লগইন করা ইউজার (Student, Teacher, Admin) কোর্স লিস্ট দেখতে পারবে
    [HttpGet]
    [Authorize]
    public IActionResult GetAllCourses()
    {
        return Ok(new[] { "Data Structures", "Algorithms", "Database Systems" });
    }

    // ২. কোর্স তৈরি করতে পারবে কেবল Teacher অথবা Admin
    [HttpPost]
    [Authorize(Roles = "Admin,Teacher")]
    public IActionResult CreateCourse([FromBody] string courseName)
    {
        return Ok(new { message = $"কোর্স '{courseName}' সফলভাবে তৈরি হয়েছে।" });
    }

    // ৩. কোর্স ডিলিট করতে পারবে শুধুমাত্র Admin
    [HttpDelete("{id}")]
    [Authorize(Roles = "Admin")]
    public IActionResult DeleteCourse(int id)
    {
        return Ok(new { message = $"কোর্স আইডি {id} ডিলিট করা হয়েছে।" });
    }
}

৬. কোডের লাইন-বাই-লাইন ব্যাখ্যা

[Authorize] মেথডের ওপরে শুধু [Authorize] থাকলে রোল দেখা হয় না—টোকেন ভ্যালিড হলেই যে কেউ এক্সেস পাবে।
[Authorize(Roles = "Admin,Teacher")] কমা দিয়ে একাধিক রোল দেওয়া হলে এটি OR কন্ডিশন হিসেবে কাজ করে। অর্থাৎ ইউজারের রোল Admin অথবা Teacher যেকোনো একটি হলেই সে কোর্স তৈরি করতে পারবে।
[Authorize(Roles = "Admin")] কোর্স ডিলিট করার মতো ঝুঁকিপূর্ণ অপারেশনে কঠোরভাবে কেবল Admin রোলধারীদেরকেই ঢুকতে দেওয়া হচ্ছে। কোনো Teacher যদি এটা কল করে, সাথে সাথে 403 Forbidden রেসপন্স পাবে।

৭. কমন ভুলগুলো (Common Mistakes)

রোল অথরাইজেশনে যেসব ভুল সচরাচর হয়:
  • স্পেলিং ও কেস সেনসিটিভিটি ভুল: টোকেনে ক্লেইম দিয়েছো "admin" (স্মল লেটার), কিন্তু কন্ট্রোলারে লিখেছো Roles = "Admin" (ক্যাপিটাল লেটার)। সি-শার্পে বাই-ডিফল্ট এটি কেস-সেনসিটিভ হতে পারে, তাই রোল সবসময় কনসিস্টেন্ট কনস্ট্যান্ট স্ট্রিং আকারে রাখবে।
  • ClaimTypes.Role ব্যবহার না করা: টোকেন বানানোর সময় ক্লেইম কি হিসেবে ইচ্ছামতো "my_role" না দিয়ে সবসময় স্ট্যান্ডার্ড ClaimTypes.Role ব্যবহার করবে। এতে .NET-এর বিল্ট-ইন [Authorize(Roles = "...")] কোনো অতিরিক্ত কনফিগার ছাড়াই স্বয়ংক্রিয়ভাবে রোল রিড করতে পারে।

৮. শর্ট সামারি (Short Summary)

মূল টেক-অ্যাওয়ে:

১. [Authorize(Roles = "Role1,Role2")] দিয়ে খুব সহজেই রোল-বেজড গার্ড বসানো যায়।

২. রোল না মিললে সার্ভার 403 Forbidden রেসপন্স প্রদান করে।

৩. ক্লেইমে রোল যুক্ত করার সময় স্ট্যান্ডার্ড ClaimTypes.Role ব্যবহার করা বেস্ট প্র্যাকটিস।
