JWT Structure ও Claims Deep Dive

পড়ার সময়: ৭ মিনিট
মডিউল: ০৩

১. এটা কী? (What is JWT?)

JWT-এর পূর্ণরূপ হলো JSON Web Token। এটি একটি ওপেন স্ট্যান্ডার্ড (RFC 7519) যা দুই পক্ষের (যেমন: তোমার React/Angular ক্লায়েন্ট এবং ASP.NET Core সার্ভার) মধ্যে সিকিউরভাবে তথ্য আদান-প্রদান করতে ব্যবহৃত হয়।

আর Claim কী? Claim হলো সহজ ভাষায় user সম্পর্কে কিছু information, যেমন User ID, Email, Role ইত্যাদি। টোকেন তৈরি করার সময় সার্ভার ইউজারের এসব তথ্য টোকেনের ভেতরে Claim হিসেবে গুঁজে দেয়।

এখানে লাল অংশটি Header, বেগুনি অংশটি Payload এবং নীল অংশটি হলো Signature।

২. কেন দরকার? (Why do we need JWT?)

আগের দিনের ট্রেডিশনাল ওয়েব অ্যাপ্লিকেশনে Session-based Authentication ব্যবহার করা হতো। সেখানে সার্ভারের মেমোরিতে বা ডেটাবেসে প্রত্যেকটি ইউজারের Session ID স্টোর করে রাখা লাগত। কিন্তু আধুনিক স্কেলেবল সিস্টেমে এর বেশ কিছু অসুবিধা আছে:

  • সার্ভারের মেমোরি খরচ: ১০ লাখ ইউজার একসাথে লগইন থাকলে সার্ভারের RAM-এ ১০ লাখ সেশন ধরে রাখতে হয়।
  • Microservices ও Load Balancing-এ ঝামেলা: যখন একাধিক সার্ভার থাকে (Load Balancer-এর পেছনে), তখন Server A-তে লগইন করা ইউজারের রিকোয়েস্ট Server B-তে গেলে সে ইউজারকে চিনতে পারে না (Sticky Session ছাড়া)।
  • মোবাইল অ্যাপস ও ক্রস-ডোমেইন ফ্রেন্ডলি নয়: সেশন কুকির ওপর নির্ভরশীল, যা বিভিন্ন থার্ড-পার্টি সার্ভিস বা মোবাইল অ্যাপে সহজে কাজ করে না।

JWT হচ্ছে Stateless (সার্ভারহীন স্মৃতি): সার্ভার টোকেন ইস্যু করার পর নিজের মেমোরিতে কিছুই জমিয়ে রাখে না! ইউজার নিজেই তার টোকেন বহন করে আনে। সার্ভার শুধু Signature চেক করে নিশ্চিত হয় টোকেনটি আসল কি না। ফলে ব্যাকএন্ড সার্ভার আনলিমিটেড স্কেল করা যায়।

৩. এটা কীভাবে কাজ করে? (How does it work?)

একটি JWT টোকেন মূলত ৩টি পার্ট নিয়ে গঠিত:

১. Header (হেডার) এতে টোকেনের মেটাডাটা থাকে—টোকেনের টাইপ (JWT) এবং কোন অ্যালগোরিদম দিয়ে Signature করা হয়েছে (যেমন: HMAC SHA256 বা RSA)।
২. Payload (পে-লোড) এখানেই মূল তথ্য বা Claims থাকে (যেমন: User ID, Name, Role, Token Expiration Time)। এটি Base64Url দিয়ে এনকোড করা থাকে, তাই যে কেউ এটা ডিকোড করে ভেতরের তথ্য পড়তে পারে।
৩. Signature (ডিজিটাল স্বাক্ষর) এটিই টোকেনকে সুরক্ষিত করে! সার্ভার তার নিজস্ব গোপন চাবি (Secret Key) দিয়ে Header এবং Payload-কে হ্যাশ করে এই Signature তৈরি করে। যদি কোনো হ্যাকার Payload-এর ভেতরের Role পরিবর্তন করে "Admin" বানাতে চায়, তাহলে Signature মিসম্যাচ হয়ে যাবে এবং সার্ভার সাথে সাথে রিকোয়েস্ট বাতিল করবে!

৪. একটা সহজ বাস্তব উদাহরণ (Real-Life Example)

বিশ্ববিদ্যালয়ের সিলমোহর মারা প্রশংসাপত্র বা সার্টিফিকেট

ধরো তুমি ভার্সিটি থেকে পাশ করার পর ভাইস চ্যান্সেলরের অফিশিয়াল সিল এবং স্পেশাল স্বাক্ষরিত একটি প্রশংসাপত্র (Certificate) নিলে।

এই সার্টিফিকেটের ভেতরে তোমার নাম, সিজিপিএ এবং ডিপার্টমেন্ট স্পষ্টভাবে লেখা আছে (এটা হলো Payload বা Claims)। যে কেউ সার্টিফিকেট হাতে নিলেই পড়তে পারছে তুমি কোন ডিপার্টমেন্টের।

কিন্তু কেউ কি ইচ্ছে করলেই কলম দিয়ে সিজিপিএ ৩.০০ কেটে ৩.৯৯ বানিয়ে ফেলতে পারবে? পারবে হয়তো, কিন্তু নিচে যে বিশেষ সিকিউর সিলমোহর আর ভিসি স্যারের জেনুইন স্বাক্ষর আছে (এটা হলো Signature), চাকরিদাতা যখন সেই স্বাক্ষরের সাথে অফিশিয়াল সিলের মিল পাবে না, তখনই জালিয়াতি ধরা পড়ে যাবে!

সার্ভারের কাছেও এমন একটা স্পেশাল Secret Key থাকে যা অন্য কেউ জানে না। তাই ক্লায়েন্ট টোকেন নিয়ে এলেও কেউ ভেতরের তথ্য কারচুপি করতে পারে না।

৫. কোড এক্সাম্পল (C# / ASP.NET Core)

নিচে C#-এ কীভাবে Claims সাজিয়ে একটি সিকিউর JWT টোকেন জেনারেট করতে হয় তার কোড দেখানো হলো:

Services/JwtTokenService.cs 
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using System.Text;
using Microsoft.IdentityModel.Tokens;

public class JwtTokenService
{
    private readonly IConfiguration _configuration;

    public JwtTokenService(IConfiguration configuration)
    {
        _configuration = configuration;
    }

    public string GenerateToken(User user)
    {
        // ১. Claims তৈরি করা (User-এর প্রয়োজনীয় তথ্য টোকেনে রাখা)
        var claims = new List<Claim>
        {
            new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()),
            new Claim(ClaimTypes.Name, user.Username),
            new Claim(ClaimTypes.Email, user.Email),
            new Claim(ClaimTypes.Role, user.Role)
        };

        // ২. appsettings.json থেকে Secret Key নিয়ে সিমেট্রিক কি তৈরি করা
        var secretKey = _configuration["JwtSettings:SecretKey"];
        var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(secretKey));
        var credentials = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

        // ৩. Token Descriptor তৈরি করা
        var tokenDescriptor = new SecurityTokenDescriptor
        {
            Subject = new ClaimsIdentity(claims),
            Expires = DateTime.UtcNow.AddHours(2),
            Issuer = _configuration["JwtSettings:Issuer"],
            Audience = _configuration["JwtSettings:Audience"],
            SigningCredentials = credentials
        };

        // ৪. টোকেন তৈরি ও স্ট্রিং-এ রূপান্তর
        var tokenHandler = new JwtSecurityTokenHandler();
        var token = tokenHandler.CreateToken(tokenDescriptor);

        return tokenHandler.WriteToken(token);
    }
}

৬. কোডের লাইন-বাই-লাইন ব্যাখ্যা

চলো কোডের প্রতিটি সেকশন একদম পয়েন্ট আকারে বুঝে নেই:

new Claim(ClaimTypes.Role, user.Role) এখানে আমরা user-এর role-টা একটা claim হিসেবে JWT-এর মধ্যে রাখছি। যদি user-এর role Admin হয়, তাহলে পরে authorization-এর সময় server এই role information ব্যবহার করতে পারবে। প্রতি রিকোয়েস্টে আলাদা করে ডেটাবেসে গিয়ে "রহিম কি অ্যাডমিন?" কুয়েরি করতে হবে না।
new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()) স্ট্যান্ডার্ড অনুযায়ী NameIdentifier ব্যবহার করা হয় ইউজারের ইউনিক প্রাইমারি কি (User ID) রাখার জন্য। পরবর্তীতে কন্ট্রোলারে User.FindFirstValue(ClaimTypes.NameIdentifier) দিয়ে সহজে ইউজারের আইডি পাওয়া যাবে।
new SymmetricSecurityKey(Encoding.UTF8.GetBytes(secretKey)) আমাদের সিক্রেট স্ট্রিং-কে বাইট অ্যারেতে রূপান্তর করে একটি ক্রিপ্টোগ্রাফিক কি তৈরি করা হচ্ছে। মনে রাখবে, এই কি-টি অন্তত ২৫৬ বিট (৩২ অক্ষর) লম্বা হওয়া উচিত।
new SigningCredentials(key, SecurityAlgorithms.HmacSha256) এখানে আমরা বলছি: "সার্ভারের এই সিক্রেট কি দিয়ে এবং HMAC-SHA256 অ্যালগরিদম ব্যবহার করে টোকেনটিতে ডিজিটাল স্বাক্ষর (Signature) সিল মারো।"
Expires = DateTime.UtcNow.AddHours(2) টোকেনটির মেয়াদ নির্ধারণ করা হচ্ছে (যেমন: ২ ঘণ্টা)। মেয়াদ শেষ হয়ে গেলে টোকেন ইনভ্যালিড হয়ে যাবে এবং ইউজারকে রিফ্রেশ টোকেন দিয়ে নতুন টোকেন নিতে হবে।
tokenHandler.WriteToken(token) অবজেক্ট আকারে তৈরি হওয়া টোকেনটিকে চূড়ান্তভাবে সেই ডট (.) সংযুক্ত তিনটি অংশের কমপ্যাক্ট স্ট্রিং-এ পরিণত করে ক্লায়েন্টের কাছে রিটার্ন করা হচ্ছে।

৭. কমন ভুলগুলো (Common Mistakes)

JWT নিয়ে যেসব মারাত্মক ভুল কখনোই করা যাবে না:
  • Payload-এ পাসওয়ার্ড বা সেনসিটিভ ডেটা রাখা: মনে রাখবে, JWT টোকেন এনক্রিপ্টেড নয়, এটি শুধু Base64Url এনকোডেড। jwt.io-তে যে কেউ পেস্ট করলেই ভেতরের Payload দেখে ফেলতে পারবে। তাই পাসওয়ার্ড, পিন কোড বা ক্রেডিট কার্ড নম্বর ভুলেও Claims-এ রাখবে না!
  • দুর্বল Secret Key ব্যবহার করা: Secret Key যদি হয় "mysecret123", তাহলে ব্রুট-ফোর্স অ্যাটাক দিয়ে হ্যাকার সহজেই তোমার কি বের করে নকল টোকেন সাইন করে ফেলতে পারবে। সবসময় দীর্ঘ, কমপ্লেক্স সিক্রেট কি এনভায়রনমেন্ট ভ্যারিয়েবলে রাখবে।
  • টোকেনের লাইফটাইম অতিরিক্ত বড় রাখা: Access Token-এর মেয়াদ ৭ দিন বা ১ মাস রাখা অত্যন্ত ঝুঁকিপূর্ণ। টোকেন চুরি হলে ওই সময় পর্যন্ত হ্যাকার সিস্টেমে ঢুকতে পারবে। Access Token সবসময় কম সময় (যেমন: ১৫ মিনিট থেকে ১ ঘণ্টা) রাখা উচিত এবং সাথে Refresh Token ব্যবহার করা উচিত।

৮. শর্ট সামারি (Short Summary)

এক নজরে মনে রাখার মতো ৩টি কথা:

১. JWT মূলত ৩টি অংশ দিয়ে গঠিত: Header.Payload.Signature।

২. Claim হলো ইউজারের পরিচয় সম্পর্কিত তথ্য (যেমন: ClaimTypes.NameIdentifier, ClaimTypes.Role)।

৩. Signature-এর কারণে ক্লায়েন্ট বা হ্যাকার পে-লোডের ডেটা পরিবর্তন করতে পারে না। ডেটা পরিবর্তন করলেই সিগনেচার ফেইল করে।
